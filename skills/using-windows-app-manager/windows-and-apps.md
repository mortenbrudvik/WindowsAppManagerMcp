# Windows and Applications

Read this when you find, launch, move, resize, focus or close windows, or start programs (and list the installed ones).

Ending an app or a process (`close_application`, `kill_process`) is in the core's [Safety Rules](SKILL.md#safety-rules-read-first); the process tools (`list_processes` too) are in [tools.md](tools.md), under App Launch.

## Find

- **Windows:** prefer naming the window with a `window` selector in the call that acts on it, over copying a raw `handle` from an earlier listing: `{"processName": "notepad"}`, `{"processName": "msedge", "titleContains": "Inbox"}`, `{"foreground": true, "processName": "notepad"}` (the window in front, if it is Notepad). `{"foreground": true}` alone names no window: input tools treat it as no `windowHandle`, close tools refuse it, respond_to_dialog, file_dialog, get_desktop_state and get_active_popups take it as no window named (a press other than `cancel`, and file_dialog, are refused; your own host in front is not read), and `allowHostTarget` needs the window named by handle; `get_browser_url` takes it alone as the browser in front (`NoBrowserInForeground` when your terminal is in front). `processName` is the whole process name (more reliable than titles, which change; `processNameContains: true` for a part); `titleEquals` and `titleRegex` pin a title exactly. A selector must name exactly one window, so it never acts on the first of several. To look before you act, `find_windows` takes the same filters (plus `visibleOnly`, `includeToolWindows`, `includeShell`, `sort` and `limit`, which a selector refuses with `InvalidArguments`) and `get_window_info` reads one window (`detail: "full"` says whether it is in front, enabled, responding, its DPI and client area); `get_foreground_window` says what is in front. When you do keep a `handle`, pass it later as `{"handle": ..., "processId": ...}` so a window that closed and whose handle was reused is refused (`HandleMismatch`) instead of acted on.
- **A program that is not running yet:** `launch_application` with `waitForWindow: true` returns the `window` it opened, whichever process owns it (a browser, Calculator or VS Code instance the launcher handed off to), with `launchStatus`: `windowObserved` (a new window), `reusedExistingWindow` or `openedInTab` (single-instance and tabbed apps such as Windows 11 Notepad, Terminal, VS Code and Explorer reuse a window that was already open). To start an installed app, take its `appId` (a packaged app, which then returns its own `processId` and needs no `expectWindow`) or `path` from `list_installed_apps`; never guess a Store app's ID. For a Settings page (`ms-settings:...`) or a document, pass `expectWindow` (`processName` or `titleContains`, each matched as a part of the name or title, ignoring case: unlike a selector's `processName`, `Code` also matches `Code - Insiders`) so the wait can recognise its window.
- **Launch and arrange in one call:** add `placement` (`{"snap": "left_half", "monitor": "left", "focus": true}`, or `bounds`, or `state`) instead of following the launch with `find_windows`, `snap_window` and `focus_window`; it waits for the window, places it, places it again if the app restores its own saved bounds, and returns `placement.finalBounds`, `finalState` and `focused`. Add `reuseExisting: true` to use a window of the app that is already open (`launchStatus` `alreadyOpen`, nothing started) instead of opening a second copy; with a file or folder argument only a window whose title shows that file or folder name counts (a path shown with it must be the launched one, but a title often shows the name alone: when `warning` says only the name matched, check the window before acting), a web address needs `expectWindow.titleContains` (the page sets its title) and, when the address itself is launched rather than passed to a browser's .exe, `expectWindow.processName` too, as a Store app or document does. When `placement.errorCode` is set the app was still launched: arrange the window with the window tools, never launch again.

## Act

- **Windows:** the window tools take `window` (a selector) or the exact `handle`, never both (`snap_window`, `set_window_bounds`, `set_window_state`, `move_window_to_monitor`, ...); their result's `handle` is the window they acted on. `set_window_bounds` takes `x` and `y` to move a window (it keeps its size), `width` and `height` to resize it (its corner stays, and it is not raised unless `bringToFront: true`), or all four. Close with `close_window`.

Snapping, monitors and layouts are in [layouts-and-monitors.md](layouts-and-monitors.md); waiting for a window to open, close or change in [waiting.md](waiting.md).

## Launch and Position an App

1. **Find and act in one call:** `launch_application` with `placement` (`snap` or `bounds`, `monitor` such as `"right"` for another monitor, `focus: true` to bring it in front) and `reuseExisting: true` to use a window that is already open
2. **Verify:** check `placement.finalBounds` (the visible frame), `finalState` and `focused` in the result. If `placement.errorCode` is set, or the launch found no window (`WindowNotFound`), wait for the window with `wait_for_window` (`processName` or `titleContains`) and place it with `snap_window` or `set_window_bounds`; never launch again

## Tips

- UWP apps such as Calculator or Settings are reported under their own process (for example `CalculatorApp`), with `hostProcessName: "ApplicationFrameHost"`. End one by its own `processId`: `kill_process` refuses ApplicationFrameHost (`ProtectedProcess`), which holds the frames of every Store app
- `get_foreground_window` reports any window, including untitled menus and popups (empty `title`, check `className`)
- `close_window` returns `AccessDenied` for a window of an app running as administrator
- A dialog of the desktop shell, such as Shut Down Windows, is not protected: `close_window` cancels it
- A bare name in `launch_application` is looked up in the Windows directory, System32, `PATH` and App Paths, then as an installed app's exact (localized) name; one that is not found fails with `ExecutableNotFound`, and the name of several apps with `AmbiguousApp` (use an `appId` or path from `list_installed_apps`). A command interpreter starts only without arguments, a script never, and a Chromium, Electron or VS Code switch that runs code or opens remote control is refused for any program (`UnsafeChromiumSwitch`; see [Other failure modes](errors.md#other-failure-modes)); a packaged app gets arguments only when it is no interpreter. `runAsAdmin` starts an `.exe` elevated after the user's approval; its window then refuses your input (`TargetElevated`). Without `workingDirectory`, the program starts in its own folder
