# Waiting

Read this when you wait for a window or dialog to open, close, come to the front, minimize, maximize or change its title, for several windows of an app at once, for a control to appear, change or go, or for the screen to change.

There is no sleep tool, and you do not need one. Wait on the server with `wait_for_window` (windows) or `wait_for_element` (controls) instead of guessing a delay or calling `find_windows` or `find_ui_elements` again and again; `launch_application` with `waitForWindow: true` already waits for a launch's window (`waitTimeoutMs`).

- **A dialog or window your action opens:** before the action, read the matching windows (`find_windows`), then call `wait_for_window` with the selector and their handles as `excludeHandles`, so the window that was already there does not count and a dialog that opened before the wait started still does (`newOnly` would miss it). An untitled dialog needs `className` (`#32770`) or `includeUntitled`.
- **A window that should close:** `condition: "gone"` (after `close_window` reports `stillOpen`, or after a button that closes a dialog). A `warning` means the selector matched nothing to begin with: check it.
- **A window that should come to the front, on screen, or be minimized or maximized:** `condition: "foreground"`, `"visible"`, `"minimized"` or `"maximized"`.
- **Several windows at once** (an app that opens, closes, minimizes or restores a set of windows): the selector is a set, every matching window counts. Before you act, read the matching windows (`find_windows`) and pass their handles as `excludeHandles`; that also keeps windows of the app that were already open, such as the user's own browser windows, out of the set. Then, in one call each:
  - N windows opened: `count: {"exactly": N}` (or `{"atLeast": N}`); `candidates` lists them with each window's `state`, `visibleBounds`, `monitorId` and `zone`.
  - all closed: `condition: "gone"`.
  - all minimized: `condition: "minimized"`, `all: true`.
  - all restored: `condition: "visible"`, `all: true`, not a normal state: a window that was maximized comes back maximized.
  - With `all` or `count`, the same windows must hold for `stableMs`, so a window that comes or goes starts the time again. A timeout lists the set as last seen, each window with its `state`, so you see which one is missing or did not change.
  - Windows that need different conditions: send one wait each, together in one turn, with any other reads; a wait does not hold up other calls.
- **A save or navigation:** `condition: "title_changed"` with the window's `handle` and the title you read before acting as `previousTitle`, or `exists` with `{"handle": ..., "titleContains": "report.txt"}` for a title you know.
- **Right after a launch:** `condition: "input_idle"` is best effort (Windows reports it once per process, never for console programs); wait for the control you need with `wait_for_element` before you type.
- **A control inside a window:** `wait_for_element` with the window and find_ui_elements' criteria (it waits for the window first, so it covers a window that is still opening), or with a `ref` you already have. `condition`: `exists` (default), `gone` (a spinner or "Loading" text), `enabled` (a button that waits for validation), `visible`, `focused`, `name_equals` / `value_equals` with the exact `expected` text (a status label, a field's value after `type_text`; a password field's value is never read, so check it another way), `toggle_state` with `expected` `on`/`off`. The result's `element` has the `ref` and `clickPoint` to act on next. `ElementStale` or `AmbiguousElement` from a `ref`: find the element again; never act on a look-alike.
- **When UI Automation has nothing to wait on** (a canvas app, a game, a remote desktop, a chart that renders): `wait_for_visual`, in the opt-in `visual` toolset, waits until a window, region or monitor changes on screen (`condition: "changed"`) or stops changing (`"stable"`, for `stableMs`), and returns `changedRegions` as rectangles, never an image. Before you act, capture the target with `output: "metadata"` (no image tokens), then act, then `wait_for_visual` with `since` set to that `captureId`: without it the baseline is the first frame after your action, so a fast change is missed. Raise `minChangedPercent` a little to ignore a clock or spinner. Windows of denied apps over the target are left out of the comparison (`maskedWindows`), so their changes never count. Prefer `wait_for_element` and `wait_for_window` whenever there is an element or window to wait for.

`wait_for_window`'s condition must hold for `stableMs` (300 by default, which skips splash screens); a result with `satisfied: true` and no `window` means several windows match, or `all` or `count` was used: `matchCount` says how many, and `candidates` lists up to 20; pick one by handle. `wait_for_element`'s condition counts as soon as one check sees it, and `gone` as soon as one complete search finds no match, unless you pass `stableMs` (0 by default): then it must hold at every check for that long, so a list that is re-created does not count as `gone` in the gap. A timeout is an error (`WaitTimedOut`, with `timedOut: true` and the window as last seen, or for `wait_for_element` the element as last seen and `lastObservedState`): do not go on as if the window or control were there; look at what is on screen, wait again, or ask the user.
